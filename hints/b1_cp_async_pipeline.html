B1 · cp.async 多级流水：commit / wait_group 与 K 循环时间线

Ampere 让“搬运”变成异步：线程发出 cp.async 就去算别的，搬运按“组”提交、按“除最新 N 组外都到齐”来等。多级 ring buffer 把一块数据的几百个周期延迟藏在前面几块的计算后面。

题面速览

  • 在系统中的位置：CUTLASS sm80 的主循环 sm80_mma_multistage.hpp：prologue 先发 Stages−1 块，之后每轮 cp_async_wait<Stages-2>() → __syncthreads() → 发下一块 → 算。PTX 包装在 cp_async_fence（commit_group）和 cp_async_wait。G2 在 5090 上写的就是这段。
  • 你要实现：CpAsyncQueue（一个线程的 cp.async 组语义）、multistage_ops(T, S)（主循环的操作序列）、simulate(T, S, L, C)（假时钟上的时间线）。
  • 难点在这几条规则：
    1. wait_group n 等的是已提交的组：除最新 n 组外全部完成；没 commit 的拷贝不算。
    2. 空组也要 commit：尾部没有新块可发时照样 commit，否则 wait<S-2> 等的不再是你以为的那一块。
    3. 新块写进 slot (k+S-1) % S = (k-1) % S，也就是上一轮刚算完的那块。
    4. 稳态周期 ≈ max(C, L / (S-1))。

验收要点：wait_group 留下最新 n 组 · 未提交的不等 · 空组也算组 · n < 0 报错 · S=3、T=4 的精确操作序列 · S=1 同步 · 每次 mma 读的块都已到齐 · 不覆盖还要用的 slot · 三组精确时间线 · stage 越多不会更慢。

直觉与类比

类比 · 回转寿司的传送带

厨房（HBM）做一盘寿司要 L 分钟才能送到你面前，你吃一盘要 C 分钟。同步的吃法：点一盘、干等、吃完再点——大部分时间在等。cp.async 多级流水是传送带上同时放 S−1 盘：坐下时先点 S−1 盘（prologue），之后每吃完一盘就再点一盘（发下一块），保证传送带上一直有 S−1 盘在路上。只要 (S−1)·C ≥ L，你永远不用等。commit_group 是“这几样算一单”，wait_group n 是“除了最近点的 n 单，前面的都上齐了再开吃”。最后几轮没东西可点了也要“报一张空单”，不然你数单子的时候会数错。

逐步演示

▶ T = 4 个 K 块、S = 3 级
1. prologue

load 0, commit, load 1, commit：2 个组在路上。

2. k = 0

已提交 2 组，wait 1 → 最老的 1 组完成 → 驻留 {0}。然后 load 2, commit，mma 0。

3. k = 1

已提交 3 组（去掉已等完的），wait 1 → 驻留 {0, 1}。load 3, commit，mma 1。

4. k = 2

没有新块可发（2 + 2 = 4 ≥ T），但照样 commit 一个空组。wait 1 → {0, 1, 2}，mma 2。

5. k = 3

wait 1 → {0, 1, 2, 3}：多亏了 k = 2 时的空组，“除最新 1 组外”里包含了块 3 那一组。少了空组，这里块 3 不保证到齐。

S = 4 时 (S−1)·C = 120 ≥ L = 100，延迟完全藏住，之后再加 stage 没有用（只会多占 SMEM）。S = 3 时 80 < 100，每两轮要等一次。

易错点

  • wait_group 也等了未提交的拷贝。 真实硬件不会；忘了 commit 的拷贝永远“不保证到齐”（test_uncommitted_copies_are_not_waited）。
  • 尾部不提交空组。 test_every_mma_reads_a_resident_tile 在 T < S 和 T ≫ S 的多种组合下逐个检查。
  • 用 wait_group 0。 正确，但把流水变成了同步：每轮都等最新的那块，延迟没藏住。
  • 新块写进 k % S。 那是本轮要算的块；test_loads_never_overwrite_a_slot_still_needed 抓这个。
  • wait 没推进时钟，或推进到了错误的组。 要用“需要完成的那些组里最晚落地的时刻”。

关键问题

  1. 第 k 轮 wait 之前一共提交了几组？wait S-2 之后哪些块一定到齐？
  2. 为什么是 S−2 而不是 S−1？
  3. 稳态下一轮多长？什么时候再加 stage 没用？
  4. 真实 kernel 里 wait 之后为什么还要 __syncthreads()？
L2思路与常见坑拆解与常见坑（中度剧透）
  • 队列：_open（当前组）、_groups（已提交未确认的组，老→新）、resident。wait_group(n)：done = groups[:-n] if n else groups。注意 [:-0] 是空列表！
  • multistage_ops：S == 1 单独处理；否则 prologue range(S-1)（s < T 才 load，总是 commit），主循环 wait S-2 → (load) → commit → mma。
  • simulate：同样遍历 ops；用列表记录“当前未提交组的落地时刻”，commit 时整体推进 groups，wait 时取 max。
L3详解：答案几乎是答案（重度剧透）
关键问题答案
  1. (S−1) + k 组（prologue S−1 组 + 前 k 轮每轮 1 组）。wait S-2 后前 k+1 组完成，也就是块 0..k。
  2. 第 k 轮要用的是第 k+1 组（从 1 数）。总共 (S−1)+k 组，留下最新 S−2 组，正好前 k+1 组完成。用 S−1 只保证块 0..k−1。
  3. max(C, L/(S−1))；当 (S−1)·C ≥ L 时已是 C，再加 stage 只会多占 SMEM、降低 occupancy——G2 在 5090 上就测得 2 级比 3、4 级快。
  4. 两个原因：(a) wait_group 只保证本线程发的拷贝到齐，别的线程搬的那部分要靠 barrier 才能看到；(b) 保证所有 warp 都读完了上一轮的 slot，才能覆盖它。

"""B1 · cp.async multistage pipeline: commit / wait_group and the K-loop timeline — reference solution.

Ampere 的 `cp.async` 让线程发出一次 global → shared 拷贝后立刻去干别的；拷贝按“组”提交
（`cp.async.commit_group`），再用 `cp.async.wait_group N` 等到“除最新 N 组以外”的组全部落地。
CUTLASS 的 sm80 multistage 主循环就是：prologue 先发 Stages−1 块，之后每轮
“等最老的一块 → 发最新的一块 → 算”。这道题实现这套组语义、生成主循环的操作序列，并在假时钟上
算出总时间，看 stage 数怎么把 load 延迟藏起来。

CpAsyncQueue（模拟一个线程的 cp.async 状态）：
- cp_async(tile)：把 tile 加进“当前未提交的组”。
- commit_group()：把当前组（可以是空组）封口，放到已提交组的末尾。
- wait_group(n)：除最新的 n 个已提交组外，其余已提交组全部完成；**未提交**的拷贝不受影响。
  返回此时所有已落地 tile 的集合（set）。n < 0 抛 ValueError。
- resident：已落地 tile 的集合。

multistage_ops(T, S) -> list[tuple]：T 个 K 块、S 个 stage 的操作序列，元素为
("load", t) / ("commit",) / ("wait", n) / ("mma", t)。
- S == 1（完全同步）：每个 k：load k, commit, wait 0, mma k。
- S ≥ 2：prologue 对 s = 0..S−2：若 s < T 则 load s；然后**总是** commit。
  主循环对 k = 0..T−1：wait S−2；若 k+S−1 < T 则 load k+S−1；然后**总是** commit；最后 mma k。
- S < 1 抛 ValueError。

simulate(T, S, L, C) -> dict：按 multistage_ops 在假时钟上执行。load 在当前时刻发出、L 个周期后落地，
发出本身不花时间；commit 不花时间；wait n 把时钟推进到需要完成的那些组里最晚落地的时刻（若更晚）；
mma 花 C 个周期。返回 {"total": 结束时刻, "mma_start": [每块 mma 的开始时刻], "util": T·C / total}。

API
    CpAsyncQueue()          .cp_async(tile) .commit_group() .wait_group(n) -> set .resident
    multistage_ops(T, S) -> list[tuple]
    simulate(T, S, L, C) -> dict
"""
from __future__ import annotations


class CpAsyncQueue:
    def __init__(self):
        """空队列：没有已提交组，没有已落地 tile。"""
        self._open: list[int] = []
        self._groups: list[list[int]] = []    # 已提交、尚未确认完成的组（老 → 新）
        self.resident: set[int] = set()

    def cp_async(self, tile: int) -> None:
        """把 tile 放进当前未提交的组。"""
        self._open.append(tile)

    def commit_group(self) -> None:
        """封口当前组（可以为空）。"""
        # 空组也要提交：wait_group 数的是“组”，不是“拷贝”。主循环尾部没有新块可发时如果不提交，
        # 组的数量就少了，wait_group<S-2> 等的就不再是你以为的那一块。
        self._groups.append(self._open)
        self._open = []

    def wait_group(self, n: int) -> set[int]:
        """除最新 n 组外全部完成；返回已落地 tile 集合。"""
        if n < 0:
            raise ValueError("wait_group n must be >= 0")
        # 只看已提交的组：还没 commit 的拷贝，哪怕 n = 0 也不保证完成——
        # 这是“我明明 wait_all 了为什么数据还是旧的”的常见原因（忘了 commit）。
        done = self._groups[:-n] if n else self._groups
        for g in done:
            self.resident.update(g)
        self._groups = self._groups[len(done):]
        return set(self.resident)


def multistage_ops(T: int, S: int) -> list[tuple]:
    """CUTLASS sm80 multistage 主循环的操作序列。"""
    if S < 1:
        raise ValueError("need at least one stage")
    ops: list[tuple] = []
    if S == 1:
        for k in range(T):
            ops += [("load", k), ("commit",), ("wait", 0), ("mma", k)]
        return ops
    # prologue：先把 S-1 块“在路上”。之后每轮发一块、用一块，在路上的块数保持不变。
    for s in range(S - 1):
        if s < T:
            ops.append(("load", s))
        ops.append(("commit",))
    for k in range(T):
        # 已提交组数 = (S-1) + k，wait S-2 → 前 k+1 组完成 → tile 0..k 都在 SMEM 里。
        ops.append(("wait", S - 2))
        # 新块写进 slot (k+S-1) % S == (k-1) % S，也就是上一轮刚算完的那块。
        # 真实 kernel 在这里还有一次 __syncthreads()：保证所有 warp 都读完了那个 slot 才覆盖它。
        if k + S - 1 < T:
            ops.append(("load", k + S - 1))
        ops.append(("commit",))
        ops.append(("mma", k))
    return ops


def simulate(T: int, S: int, L: int, C: int) -> dict:
    """在假时钟上执行 multistage_ops，返回总时间、每块 mma 开始时刻和利用率。"""
    now = 0
    open_done: list[int] = []          # 当前未提交组里各拷贝的落地时刻
    groups: list[list[int]] = []       # 已提交、未等待的组
    mma_start = []
    for op in multistage_ops(T, S):
        if op[0] == "load":
            open_done.append(now + L)
        elif op[0] == "commit":
            groups.append(open_done)
            open_done = []
        elif op[0] == "wait":
            n = op[1]
            done = groups[:-n] if n else groups
            for g in done:
                if g:
                    now = max(now, max(g))
            groups = groups[len(done):]
        else:
            mma_start.append(now)
            now += C
    # 稳态下每轮的周期 ≈ max(C, L / (S-1))：一块 load 提前 S-1 轮发出，
    # 只要 (S-1)·C ≥ L，延迟就被完全藏住，Tensor Core 只等第一块。
    return {"total": now, "mma_start": mma_start, "util": T * C / now if now else 0.0}

面试官追问 & 对照源码

  • “cp.async.ca 和 .cg 有什么区别？” .ca 在 L1 缓存，.cg 只经 L2（绕过 L1）；16 B 拷贝通常用 .cg。zero-fill 版本（src-size = 0）用于越界：SM80_CP_ASYNC_CACHEGLOBAL_ZFILL。
  • “为什么 Hopper 不用 cp.async 了？” H100 每 SM 每时钟要 4096 FLOP，每个线程算地址、发 16 B 拷贝、再 __syncthreads，占掉的线程和指令发射带宽太多。TMA 一个线程一条指令搬整个 tile，完成用 mbarrier 按字节记账（B2、B3）。
  • “FlashAttention-2 的 K/V 也是这么流水的吗？” 是：FA2 在 sm80 上用 cp.async 双缓冲 K、V（flash_fwd_kernel.h 里的 cp_async_fence / cp_async_wait），G3 为了简单用的是同步加载，留作扩展练习。
