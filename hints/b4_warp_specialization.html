B4 · Warp specialization：Pingpong vs Cooperative 与 setmaxnreg

H100 的 GEMM 里，warp 不再“既搬又算”：一个 producer warpgroup 只发 TMA，两个 consumer warpgroup 只做 wgmma 和 epilogue。Pingpong 让两个 consumer 轮流用 Tensor Core，一个做 epilogue 的时候另一个正好在算；setmaxnreg 把 producer 用不着的寄存器挪给 consumer。

题面速览

  • 在系统中的位置：CUTLASS 的 sm90_gemm_tma_warpspecialized_pingpong.hpp 和 …_cooperative.hpp。pingpong 的寄存器分配写在 LoadRegisterRequirement / MmaRegisterRequirement（40 / 232，重压力时 24 / 240），两个 consumer 用 math_wg_order_barrier 轮流进入 mainloop。FA3 在 H100 上用的是同一个思路。
  • 你要实现：pingpong_timeline、cooperative_timeline、makespan、tc_utilization、max_consumer_regs。
  • 难点在这几条规则：
    1. Tensor Core 同一时刻只服务一个 warpgroup；pingpong 下 tile i 的 mainloop 必须等 tile i−1 的 mainloop 结束。
    2. 同一个 WG 的下一个 tile 还要等它自己的 epilogue 结束（累加器寄存器要先写出去）。
    3. cooperative：两个 WG 合算一个 tile，epilogue 两人各做一半（EP/2），这段时间 Tensor Core 空着。
    4. setmaxnreg：每个 warpgroup 128 线程，128·(load + n·x) ≤ 65536，x 是 ≤ 256 的 8 的倍数。

验收要点：短 epilogue 时 Tensor Core 不停 · 长 epilogue 时等自己的 WG · cooperative 串行 · epilogue 有分量时 pingpong 更快 · 空时间线 · Tensor Core 从不被两个 WG 同时占用 · 40 → 232、24 → 240 · setmaxnreg 操作数校验。

直觉与类比

类比 · 两个厨师共用一口炒锅

一口大火炒锅（Tensor Core），两个厨师（consumer warpgroup），一个打杂（producer，只负责备菜 = TMA）。Cooperative：两个厨师一起炒一大锅，炒完一起装盘（epilogue），装盘时锅空着。Pingpong：厨师 A 炒自己那锅，炒完立刻把锅让给厨师 B，自己去装盘；B 炒完再让回给 A——只要装盘比炒菜快，锅就一直在火上。打杂的不需要大案板，于是把自己的案板空间（寄存器）让给两个厨师：40 + 232 + 232 刚好塞满 512（每线程寄存器预算 65536 / 128）。

逐步演示

▶ 4 个 tile，ML = 10，EP = 6
1. tile 0

WG0 从 0 开始 mainloop，10 时结束，接着做 epilogue（10–16）。

2. tile 1

WG1 等的是“Tensor Core 空出来”：10 时开始，20 结束，epilogue 20–26。WG0 的 epilogue 正好落在 WG1 的 mainloop 里。

3. tile 2

WG0 的条件：Tensor Core 20 空出，自己的 epilogue 16 已结束 → 20 开始。Tensor Core 一刻没停。

4. 结束

tile 3 在 30–40，最后一个 epilogue 到 46：makespan = 46，利用率 40/46 = 0.87。

5. 对比 cooperative

每个 tile 10 + 6/2 = 13，4 个 = 52，利用率 0.77。如果 EP = 15（长于 ML），pingpong 的 tile 2 要等 WG0 的 epilogue 到 25：开始时刻变成 0、10、25、35，makespan 60。

易错点

  • pingpong 里只看 Tensor Core 不看自己的 WG。 EP > ML 时会算出“WG0 还在写累加器就开始下一个 tile”（test_pingpong_long_epilogue_waits_for_own_wg）。
  • cooperative 的 epilogue 用了 EP 而不是 EP/2。 两个 WG 各写一半。
  • 以为 pingpong 永远更好。 每个 WG 的 tile 只有 cooperative 的一半大，强度更低（A1）；K 很大、epilogue 很短时 cooperative 往往更快。CUTLASS 两种都提供，由 profiler 选。
  • setmaxnreg 的值不是 8 的倍数，或超过 256。 ptxas 会直接报错（test_setmaxnreg_validates_operand）。
  • 忘了 producer 也占寄存器。 128·(40 + 2·232) = 64512，再多 8 个就超了。

关键问题

  1. pingpong 下 Tensor Core 什么时候会空闲？
  2. 为什么 cooperative 的 tile 可以更大？
  3. producer 为什么只要 24–40 个寄存器？
  4. setmaxnreg 之后 consumer 的 232 个寄存器里，累加器占多少？
L2思路与常见坑拆解与常见坑（中度剧透）
  • pingpong：维护 tc_free（上一个 mainloop 结束）和 wg_free[2]（每个 WG 上一个 epilogue 结束）；s = max(tc_free, wg_free[i % 2])。
  • cooperative：一个变量 t，每个 tile t → t + ML → t + ML + EP/2。
  • max_consumer_regs：先校验 load；x = (65536 // 128 - load) // n；向下取 8 的倍数；再 min(256, …)。
L3详解：答案几乎是答案（重度剧透）
关键问题答案
  1. 当一个 WG 的 epilogue 比另一个 WG 的 mainloop 还长（EP > ML），或者只剩最后一个 tile 的 epilogue 时。
  2. 两个 WG 合算 128×N 的 tile，每个 WG 的累加器是 64×N；pingpong 每个 WG 独占一个 tile，同样寄存器预算下 tile 是 64×N——强度更低。
  3. 它只发 TMA：算坐标、发一条指令、操作 barrier，几乎不需要数据寄存器。
  4. 64×256 的 FP32 累加器分给 128 线程 = 128 个寄存器（A1 的 accumulator_regs_per_thread），剩下的给地址、softmax（FA3）、epilogue 的转换。

"""B4 · Warp specialization on Hopper: Pingpong vs Cooperative, and the setmaxnreg register split — reference solution.

H100 的 GEMM 不再是“每个 warp 都既搬又算”：一个 producer warpgroup 只发 TMA，两个 consumer
warpgroup 只做 wgmma 和 epilogue。CUTLASS 有两种 consumer 排法：
- Cooperative：两个 consumer 合作算同一个（更大的）tile，一起做 mainloop、一起做 epilogue；
  epilogue 期间 Tensor Core 空着。
- Pingpong：两个 consumer 各算各的 tile，用一个“顺序 barrier”轮流占用 Tensor Core；
  一个做 epilogue 的时候，另一个正好在跑 mainloop。
再加上 `setmaxnreg`：producer 只需要很少寄存器，把它降下来，consumer 就能升到 232 个。

时间模型（单位任意，整数）：
- 一个“单位 tile”的 mainloop 占用 Tensor Core ML，epilogue（累加器 → BF16 → SMEM → TMA store）
  花 EP，epilogue 不用 Tensor Core。Tensor Core 同一时刻只服务一个 warpgroup。
- pingpong_timeline(n_tiles, ML, EP)：tile i 给 WG i % 2。tile i 的 mainloop 开始时刻 =
  max(tile i−1 的 mainloop 结束, 同一 WG 上一个 tile 的 epilogue 结束)（tile 0 从 0 开始）；
  mainloop 结束后该 WG 立即做 epilogue。
- cooperative_timeline(n_tiles, ML, EP)：每个单位 tile 由两个 WG 合作，mainloop 占 Tensor Core ML，
  epilogue 两个 WG 各做一半、花 EP / 2；下一个 tile 的 mainloop 在上一个 epilogue 结束后开始。
- 两个函数都返回按 tile 排序的列表，每项是字典
  {"tile", "wg", "ml_start", "ml_end", "ep_start", "ep_end"}；cooperative 的 "wg" 记为 -1（两个都参与）。
- makespan(tl) = 最后一个 ep_end（空列表为 0）；tc_utilization(tl) = Σ(ml_end − ml_start) / makespan。

寄存器（每个 warpgroup 128 线程，一个 SM 65536 个 32-bit 寄存器）：
- max_consumer_regs(load_regs, n_consumers, regs_per_sm=65536)：producer 降到 load_regs 后，每个
  consumer 线程最多能升到多少：满足 128·(load_regs + n_consumers·x) ≤ regs_per_sm 的、
  不超过 256 的最大 8 的倍数 x。load_regs 必须是 [24, 256] 内 8 的倍数，否则 ValueError。

API
    pingpong_timeline(n_tiles, ML, EP) -> list[dict]
    cooperative_timeline(n_tiles, ML, EP) -> list[dict]
    makespan(tl) -> float
    tc_utilization(tl) -> float
    max_consumer_regs(load_regs, n_consumers, regs_per_sm=65536) -> int
"""
from __future__ import annotations


def pingpong_timeline(n_tiles: int, ML: float, EP: float) -> list[dict]:
    """两个 consumer WG 轮流占用 Tensor Core。"""
    out = []
    tc_free = 0.0                 # 顺序 barrier：上一个 tile 的 mainloop 结束时刻
    wg_free = [0.0, 0.0]          # 每个 WG 上一次 epilogue 结束时刻
    for i in range(n_tiles):
        wg = i % 2
        # 两个约束：Tensor Core 要轮到我（上一个 tile 的 mainloop 完了），我自己也要空下来
        # （上一个 tile 的 epilogue 写完了，累加器寄存器可以重用）。
        s = max(tc_free, wg_free[wg])
        e = s + ML
        out.append({"tile": i, "wg": wg, "ml_start": s, "ml_end": e, "ep_start": e, "ep_end": e + EP})
        tc_free = e
        wg_free[wg] = e + EP
    # EP ≤ ML 时 Tensor Core 永不空闲（除了最后一个 epilogue）；EP > ML 时每个 tile 空出 EP − ML。
    # 代价：每个 WG 的 tile 只有 cooperative 的一半大（累加器寄存器有限），所以 tile 强度更低，
    # 对 SMEM 带宽要求更高——K 大、epilogue 相对短时 cooperative 往往更快。
    return out


def cooperative_timeline(n_tiles: int, ML: float, EP: float) -> list[dict]:
    """两个 WG 合作同一个 tile：mainloop 之后一起做 epilogue，Tensor Core 空着。"""
    out = []
    t = 0.0
    for i in range(n_tiles):
        s, e = t, t + ML
        out.append({"tile": i, "wg": -1, "ml_start": s, "ml_end": e, "ep_start": e, "ep_end": e + EP / 2})
        t = e + EP / 2
    return out


def makespan(tl: list[dict]) -> float:
    """最后一个 epilogue 结束的时刻。"""
    return max((x["ep_end"] for x in tl), default=0)


def tc_utilization(tl: list[dict]) -> float:
    """Tensor Core 忙碌时间 / 总时间。"""
    span = makespan(tl)
    return sum(x["ml_end"] - x["ml_start"] for x in tl) / span if span else 0.0


def max_consumer_regs(load_regs: int, n_consumers: int, regs_per_sm: int = 65536) -> int:
    """setmaxnreg 之后 consumer 每线程最多能拿多少寄存器。"""
    if load_regs % 8 or not 24 <= load_regs <= 256:
        # setmaxnreg 的操作数必须是 [24, 256] 内 8 的倍数，否则 ptxas 直接报错。
        raise ValueError("setmaxnreg count must be a multiple of 8 in [24, 256]")
    # 一个 warpgroup = 128 线程。CUTLASS pingpong：producer 40、两个 consumer 232：
    # 128·(40 + 2·232) = 64512 ≤ 65536。producer 降到 24 时 consumer 能到 240（HeavyRegisterPressure）。
    per_thread = regs_per_sm // 128 - load_regs
    x = per_thread // n_consumers
    return min(256, x // 8 * 8)

面试官追问 & 对照源码

  • “FA3 的 pingpong 和 GEMM 的有什么不同？” FA3 让两个 warpgroup 交替做 “GEMM（QKᵀ / PV）” 和 “softmax”，因为 softmax（MUFU 上的 exp）在 H100 上已经占 MMA 时间的一半（D3）；另外还有 warpgroup 内的重叠：本块的 softmax 和下一块的 QKᵀ 交错。
  • “Blackwell 上还需要 pingpong 吗？” 累加器在 TMEM 里、可以双缓冲（C1），MMA warp 和 epilogue warp 天然重叠，不需要把 tile 切小。CUTLASS sm100 的角色见 WarpCategory（MMA / Sched / MainloopLoad / EpilogueLoad / Epilogue）。
  • “DeepGEMM 的 FP8 kernel 怎么用 consumer 的寄存器？” 每 128 个 K 把 wgmma 的部分和取出来乘 scale 再加进 FP32 累加器（C2），所以 consumer 需要两份累加器：sm90_fp8_gemm_1d2d.cuh。
  • “5090 能做 warp specialization 吗？” 能（mbarrier + TMA 在 sm120 都有），但没有 wgmma，consumer 还是 warp 级 mma.sync，没有 setmaxnreg 的必要性那么强。
