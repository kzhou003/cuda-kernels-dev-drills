C4 · Kernel 之间：stream vs CUDA Graph vs PDL 的时间线与依赖

一步 decode 是几百个 5–30 µs 的小 kernel。kernel 写得再快，kernel 之间的空隙（CPU 发射、GPU 启动延迟、下一个 kernel 的 prologue）也会吃掉 10–30% 的时间。CUDA Graph 去掉 CPU，PDL 把 prologue 藏进上一个 kernel 的尾巴——但 PDL 只有在 graph 里才真正显出作用。

题面速览

  • 在系统中的位置：device 端 launch_dependent_grids / wait_on_dependent_grids（griddepcontrol.launch_dependents / griddepcontrol.wait）；CUTLASS GEMM 只在 producer 第一次读 global 之前 wait（pingpong.hpp L626–629）；host 端给 cudaLaunchKernelEx 加 programmaticStreamSerializationAllowed（kernel_launch.h）。推理框架：SGLang 的 RoPE kernel 开头先算索引再 griddepcontrol.wait，Python 侧默认 is_arch_support_pdl；整步 decode 用 CudaGraphRunner 录成 graph。G4 在 5090 上真测这四种方式。
  • 你要实现：timeline(kernels, mode, costs)（四种模式）、pdl_hazards（wait 之前哪些访存不安全）、guaranteed_complete（过了 wait 之后哪些上游一定完成了）。
  • 难点在这几条规则：
    1. PDL 下 kernel i 在上游触发后就能启动，但 main 必须等上游全部完成：main_start = max(start + prologue, end_{i−1})。
    2. 没有显式触发（trigger = None）时，隐式触发在上游结束时，PDL 什么也省不了。
    3. stream 模式下 CPU 每 cpu_launch 才发一个 kernel；kernel 比这还短时，CPU 是瓶颈，PDL 帮不上。
    4. griddepcontrol.wait 只等直接上游；传递性要靠中间的 kernel 自己也 wait 过。

验收要点：stream / graph / graph+PDL 的精确时间线 · 无触发时 PDL 无收益 · CPU 瓶颈下 PDL 收益很小而 graph 里收益大 · PDL 下 main 从不早于上游结束但启动更早 · 非法模式与空链 · RAW / WAR / WAW 检查 · 传递完成性。

直觉与类比

类比 · 接力赛

每个 kernel 是一棒。stream：每一棒都要等教练（CPU）喊“下一个上场”，教练喊一次要 4 秒——棒越短，教练越成瓶颈。CUDA Graph：整场比赛的出场顺序提前排好，教练只喊一次“开始”。PDL：下一棒不用站在起点干等，而是在交接区里先跑起来（prologue：系鞋带、热身、拿好自己的装备 = 初始化 barrier、预取描述符、读权重），只是接棒那一下（griddepcontrol.wait）必须等上一棒真的到了。如果上一棒根本不发信号让你进交接区（不调用 launch_dependents），那你只能在起点等。而如果教练喊人比跑一棒还慢，交接区再长也没用——这就是“PDL 只有在 graph 里才显出作用”。

2. 触发

k0 的 trigger = 0：main 一开始（11）就执行 launch_dependents。注意触发不发布任何结果，只是允许下游上 SM。

3. k1 提前启动

k1 在 11 + graph_gap = 12 启动，prologue 12–14 和 k0 的 main 重叠。

4. wait

k1 在 14 到达 griddepcontrol.wait，等 k0 全部完成（17）。

5. k1 main

k1 main 17–23。每个 kernel 的有效间隔从 graph 模式的 1 + 2 + 6 = 9 µs 缩到 6 µs：8 个 kernel 共 59 µs（graph 80，stream 92）。

易错点

  • PDL 下 main 不等上游结束。 最危险的 bug：读到上游还没写完的数据。test_main_never_starts_before_previous_end_with_pdl。
  • 没触发也算提前启动。 trigger = None 时触发点就是上游结束（test_pdl_without_trigger_gains_nothing）。
  • stream_pdl 忽略了 CPU。 下游启动 = max(cpu_i, trig_{i−1}) + launch_latency，CPU 没发出来的 kernel 不可能提前上 SM。
  • wait 之前写了上游还在读的 buffer。 ping-pong 或 in-place 的 kernel 很容易这样（WAR）；pdl_hazards 要报出来。
  • 以为 wait 等的是“所有更早的 kernel”。 只等直接上游；中间某个 kernel 不 wait 时传递性就断了（test_transitive_completion_requires_intermediate_wait）。

关键问题

  1. PDL 下一个 kernel 的有效时长是多少（相对于 graph）？
  2. 为什么 CUTLASS 把 launch_dependent_grids 放在 epilogue 开始附近，而不是 kernel 入口？
  3. 什么样的 prologue 工作可以放在 wait 之前？
  4. torch.compile 的 mode="reduce-overhead" 和 PDL 是什么关系？
L2思路与常见坑拆解与常见坑（中度剧透）
  • timeline：对每个 kernel 先算 start（四种模式各一个公式），再 main_start = start + prologue，PDL 模式再和 prev_end 取 max，end = main_start + main，最后记下 trig。
  • 输出的每个字典只要 start / main_start / end 三个键（trig 用完删掉）。
  • pdl_hazards：遇到 "wait" 就停；op.partition(":") 拆出种类和 buffer。
  • guaranteed_complete：递归；kernel i−1 是 0 或者 waits[i−1] 为真时继续往前。
L3详解：答案几乎是答案（重度剧透）
关键问题答案
  1. 在 prologue 能完全藏住、上游及时触发的情况下：graph_gap 和 prologue 都被藏住，有效时长 ≈ main（本例 6 µs vs 9 µs）。
  2. 下游 CTA 一旦启动就会占 SM 资源（寄存器、SMEM）。入口就触发会让下游 CTA 和上游的 mainloop 抢资源；在 epilogue 附近触发，下游的 prologue 正好和上游的尾巴（最后一波、epilogue 写回）重叠。G4 为了把效果放大，在入口触发。
  3. 不读上游输出、也不写上游会读的东西的工作：计算索引、初始化 SMEM / mbarrier、预取 TMA 描述符、读权重 / scale / 位置编码表（它们不是上游写的）。
  4. reduce-overhead 自动用 CUDA graph 录制，消掉 CPU 发射；PDL 是 graph 里 kernel 之间的边（programmatic edge），需要每个 kernel 自己带 griddepcontrol 指令并以 PDL 属性启动——编译器（Triton、Inductor）和框架（SGLang 的 sgl-kernel、FlashInfer 的 enable_pdl）正在逐步把它加上。

"""C4 · Between kernels: stream launches vs CUDA Graph vs Programmatic Dependent Launch (PDL) — reference solution.

一步 decode 是几百个 5–30 µs 的小 kernel。kernel 之间的空隙有三个来源：CPU 发射（每次几 µs）、
GPU 端的启动延迟（上一个 kernel 结束到下一个 kernel 的 CTA 开始跑）、以及下一个 kernel 自己的
prologue（分配 SMEM、初始化 mbarrier、预取 TMA descriptor、读权重）。
- CUDA Graph 一次性提交整条链：消掉 CPU 发射，并把 GPU 端空隙压小。
- PDL（sm90+）让下一个 kernel 在上一个 kernel 调用 `griddepcontrol.launch_dependents` 之后就启动，
  先跑不依赖上游输出的 prologue，到 `griddepcontrol.wait` 再等上游**全部完成**（含内存可见）。
所以 PDL 只有在 CPU 不是瓶颈时才有意义——也就是在 CUDA Graph 里（或 CPU 远远跑在前面时）。
这道题在假时钟上把这几种方式的时间线算出来，并检查 PDL 下哪些访存是不安全的。

给定（given）：Kernel(name, prologue, main, trigger=None)、Costs(cpu_launch, launch_latency, graph_launch, graph_gap)。
trigger 是 launch_dependents 在 main 阶段里的位置（0..1 的比例），None 表示从不显式触发（只在结束时隐式触发）。

timeline(kernels, mode, costs) -> dict：{"kernels": [{"start", "main_start", "end"}...], "total": 最后一个 end}。
记 trig(i) = main_start_i + trigger_i·main_i（trigger 为 None 时 = end_i）。每个 kernel：
main_start = start + prologue（PDL 模式见下），end = main_start + main。
- "stream"：CPU 依次发射，kernel i 在 cpu_i = (i+1)·cpu_launch 时发射完成；
  start_i = max(cpu_i, end_{i−1}) + launch_latency（i = 0 时没有 end_{−1} 项）。
- "stream_pdl"：同上，但 start_i = max(cpu_i, trig(i−1)) + launch_latency；
  main_start_i = max(start_i + prologue_i, end_{i−1})。
- "graph"：start_0 = graph_launch + launch_latency；start_i = end_{i−1} + graph_gap。
- "graph_pdl"：start_0 同上；start_i = trig(i−1) + graph_gap；main_start_i = max(start_i + prologue_i, end_{i−1})。
- 其他 mode 抛 ValueError。

pdl_hazards(ops, prev_writes, prev_reads) -> list[tuple[int, str, str]]：ops 是一个 PDL kernel 按程序顺序的操作，
元素为 "wait"、"trigger"、"compute"、"read:<buf>"、"write:<buf>"。在第一个 "wait" 之前：
读 prev_writes 里的 buf 是 "RAW"；写 prev_reads 里的 buf 是 "WAR"；写 prev_writes 里的 buf 是 "WAW"
（同时满足时报 "WAW"）。返回 (下标, op, 类型) 列表；wait 之后的操作都安全。

guaranteed_complete(i, waits) -> set[int]：kernel 0..n−1 以 PDL 链式启动，waits[j] 表示 kernel j 是否执行了
griddepcontrol.wait（kernel 0 是普通启动，视为 waits[0] = True，它之前没有 kernel）。
kernel i（i ≥ 1）通过它自己的 wait 之后，能确定已经完成的 kernel 集合：
G(i) = {i−1} ∪ (G(i−1) 若 waits[i−1] 为真，否则 ∅)，G(0) = ∅。

API
    Kernel, Costs                                         given
    timeline(kernels, mode, costs) -> dict
    pdl_hazards(ops, prev_writes, prev_reads) -> list[tuple[int, str, str]]
    guaranteed_complete(i, waits) -> set[int]
"""
from __future__ import annotations

from dataclasses import dataclass


@dataclass(frozen=True)
class Kernel:
    """一个 kernel：prologue（不读上游输出）、main（读上游输出），以及 launch_dependents 的位置。"""
    name: str
    prologue: float
    main: float
    trigger: float | None = None


@dataclass(frozen=True)
class Costs:
    """单位 µs。数值只是量级示意：CPU 每次 launch 几 µs，GPU 端启动延迟几 µs，graph 内空隙 ~1 µs。"""
    cpu_launch: float = 4.0
    launch_latency: float = 3.0
    graph_launch: float = 6.0
    graph_gap: float = 1.0


def _trig(k: Kernel, main_start: float, end: float) -> float:
    return end if k.trigger is None else main_start + k.trigger * k.main


def timeline(kernels, mode: str, costs: Costs) -> dict:
    """几种发射方式下每个 kernel 的开始 / main 开始 / 结束时刻。"""
    if mode not in ("stream", "stream_pdl", "graph", "graph_pdl"):
        raise ValueError(f"unknown mode {mode}")
    out = []
    pdl = mode.endswith("_pdl")
    for i, k in enumerate(kernels):
        prev = out[-1] if out else None
        if mode.startswith("stream"):
            cpu = (i + 1) * costs.cpu_launch
            if prev is None:
                start = cpu + costs.launch_latency
            else:
                # 没有 PDL：上一个 kernel 结束才轮到我。有 PDL：上一个触发后我就能上 SM。
                # 但 CPU 每 cpu_launch 才发出一个——kernel 比 cpu_launch 短时，CPU 才是瓶颈，PDL 救不了。
                gate = prev["trig"] if pdl else prev["end"]
                start = max(cpu, gate) + costs.launch_latency
        else:
            if prev is None:
                start = costs.graph_launch + costs.launch_latency
            else:
                start = (prev["trig"] if pdl else prev["end"]) + costs.graph_gap
        main_start = start + k.prologue
        if pdl and prev is not None:
            # griddepcontrol.wait：等上游 grid 全部完成且写回可见。prologue 被藏进了上游的尾巴里。
            main_start = max(main_start, prev["end"])
        end = main_start + k.main
        out.append({"start": start, "main_start": main_start, "end": end, "trig": _trig(k, main_start, end)})
    for o in out:
        o.pop("trig")
    return {"kernels": out, "total": out[-1]["end"] if out else 0.0}


def pdl_hazards(ops, prev_writes, prev_reads) -> list[tuple[int, str, str]]:
    """griddepcontrol.wait 之前的不安全访存。"""
    # 上游 kernel 可能还在跑：它写的东西我不能读（RAW），它读的东西我不能改（WAR），
    # 它写的东西我也不能写（WAW）。最常见的真实 bug：把 “读输入 x” 放到 wait 前面当 prologue；
    # 或者 in-place kernel 在 wait 前就写了上游还要读的残差 buffer。
    out = []
    pw, pr = set(prev_writes), set(prev_reads)
    for i, op in enumerate(ops):
        if op == "wait":
            break
        kind, _, buf = op.partition(":")
        if kind == "read" and buf in pw:
            out.append((i, op, "RAW"))
        elif kind == "write" and buf in pw:
            out.append((i, op, "WAW"))
        elif kind == "write" and buf in pr:
            out.append((i, op, "WAR"))
    return out


def guaranteed_complete(i: int, waits) -> set[int]:
    """kernel i 过了自己的 wait 之后，哪些更早的 kernel 一定已完成。"""
    # griddepcontrol.wait 只等“直接上游”那一个 grid。传递性靠上游自己也 wait 过：
    # 如果 kernel i−1 根本没调用 wait（它不读 i−2 的输出），它可能比 i−2 先结束，
    # 那 kernel i 就不能假设 i−2 的输出已经写好——读两层以前的 buffer 时要小心。
    if i <= 0:
        return set()
    g = {i - 1}
    if i - 1 == 0 or waits[i - 1]:
        g |= guaranteed_complete(i - 1, waits)
    return g

面试官追问 & 对照源码

  • “为什么 PDL 只有在 graph / compiler 层面才真正有用？” 单个 kernel 的作者无法让它生效：需要上游调用 launch_dependents、下游以 PDL 属性启动并在正确位置 wait、中间不能有 CPU 同步或别的流插进来。只有掌握整张图的人（CUDA graph 的录制者、编译器、推理框架）能保证这三件事同时成立，而且 CPU 发射开销被 graph 去掉之后，PDL 省下的 prologue 时间才成为主要部分。
  • “PDL 和 stream 上普通的 kernel fusion 怎么选？” 能融合就融合（少一次 HBM 往返）；不能融合的（比如 GEMM → attention）用 PDL 把边界压小。CUTLASS 的 epilogue visitor tree 是 GEMM 方向的融合。
  • “Rubin 有什么新东西？” 数据驱动同步：TMA 按 16 B 报告上游写的数据是否有效，下游按 tile 粒度等，而不是等整个 grid（例子 121）。
  • “CUDA graph 的代价？” 形状要固定（decode 按 batch size 分桶录多张图，见 CudaGraphRunner.capture）、显存要按最大形状预留、图里不能有 CPU 同步。
