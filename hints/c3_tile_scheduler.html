C3 · Tile 调度：wave quantization、raster swizzle、persistent、Stream-K

kernel 内部越快，“哪个 SM 算哪个 tile”越重要：最后一波只有一半 SM 有活干、同时在跑的 tile 共用不了 L2 里的数据，都会把内循环省下的时间吐回去。raster swizzle、persistent kernel、Stream-K 是 CUTLASS 的三件工具。

题面速览

  • 在系统中的位置：CUTLASS sm90 的 sm90_tile_scheduler.hpp（persistent 静态轮转 + raster order / swizzle，参数在 tile_scheduler_params.h 的 max_swizzle_size）和 sm90_tile_scheduler_stream_k.hpp（DecompositionMode：DataParallel / SplitK / StreamK / Heuristic）。Blackwell 加了硬件的 Cluster Launch Control（issue_clc_query）：运行中的 CTA“取消”一个还没启动的 CTA、接手它的坐标。
  • 你要实现：wave_stats、raster_order、wave_unique_bytes、persistent_static、stream_k、fixup_tiles、makespan。
  • 难点在这几条规则：
    1. 一波 = SM 数 × 每 SM 的 CTA 数；最后一波不满就是浪费。
    2. 条带化的 raster：m 方向每 swizzle 行一条，条带内按列走，一波 tile 变成矮胖的方块。
    3. Stream-K：把 tiles × k_iters 个 MAC 迭代按 SM 平分，区间在 tile 边界处切开。
    4. 被多个 SM 分段算的 tile 需要 fixup（部分和归约）。

验收要点：H100 上 200 个 tile 是 2 波、利用率 76% · 整除与多 CTA · 行优先 · swizzle = 2 的顺序 · raster 是置换 · swizzle 参数校验 · swizzle 减少 L2 流量 · 静态轮转 · Stream-K 小例子与 fixup · 每个 (tile, k) 恰好一次且负载差 ≤ 1 · Stream-K 比 data-parallel 快 · 空输入。

直觉与类比

类比 · 食堂打饭

170 个窗口（SM），每份饭（tile）一个窗口打。64 份饭：106 个窗口闲着（5090 上 1024³ 的 GEMM，128×128 tile，只有 37.6% 的利用率——G1 的 bench 里 1024 那一行只有 31 TF/s 就是这个原因）。persistent：窗口不关，打完一份接着打下一份，省掉每份开关窗口的时间。Stream-K：把每份饭拆成 64 勺，所有勺子平均分给窗口，一份饭可能由两个窗口各打一半，最后要合到一个碗里（fixup）。raster swizzle：同一时间打的饭尽量用同几锅菜（A 行块、B 列块），后厨（L2）不用同时备 132 锅。

图解：同一个 GEMM 的三种分法

逐步演示

▶ 3 个 tile × 4 个 k 迭代，2 个 SM
1. 平分

T = 3·4 = 12，SM s 负责 [s·12/2, (s+1)·12/2)：SM 0 是 0..5，SM 1 是 6..11。

2. 按 tile 边界切开

SM 0：(0, 0, 4)（tile 0 的全部 4 步）、(1, 0, 2)（tile 1 的前 2 步）；SM 1：(1, 2, 4)、(2, 0, 4)。

3. fixup

fixup_tiles = {1: 2}：tile 1 由 2 个 SM 各算一段，部分和写到 workspace，再由其中一个读回来相加。makespan = 6，两个 SM 完全均衡。

4. 放大到 H100

200 个 tile × 64 步、132 个 SM：data-parallel 要 2 波 = 128 步；Stream-K 每个 SM 96 或 97 步，makespan = 97，快 24%（不计 fixup 开销）。

raster swizzle 的效果（32×32 个 tile，每波 132 个，按“每波不同的 A 块 + B 块数”计，由 wave_unique_bytes 算出）：

swizzle 1 2 4 8 16
每次 k 步 L2 读的块数（8 波合计） 295 302 309 220 214

注意 2 和 4 反而比 1 略差：一波 132 个 tile 和条带形状对不齐时，一波会横跨两个条带。真实调度器按 SM 数和 cluster 形状来选 swizzle，CUTLASS 里叫 max_swizzle_size。

易错点

  • 最后一波按满波算。 last_wave 是剩下的 tile 数，efficiency = tiles / (waves·slots)。
  • raster 条带内按行走。 那就和不 swizzle 一样了；题面规定条带内按列（n）走、每列再走完条带内的行。
  • Stream-K 用 ceil 给每个 SM 分。 会让最后一个 SM 少很多；用 s·T // n 的整数切分，负载差 ≤ 1。
  • 段的 k 范围不在 tile 边界切开。 一个段跨两个 tile 是错的（0 <= b < e <= k 检查）。
  • fixup 把只被一个 SM 算的 tile 也算进去。 只统计参与 SM 数 > 1 的。

关键问题

  1. 5090 上 4096³ 的 bf16 GEMM、128×128 tile，利用率是多少？
  2. 为什么条带内按列走能减少 L2 流量？
  3. Stream-K 的 fixup 有什么代价？什么时候不值得？
  4. persistent kernel 除了“不用重新启动 CTA”，还省了什么？
L2思路与常见坑拆解与常见坑（中度剧透）
  • raster_order：for m0 in range(0, M, s)，rows = range(m0, min(m0+s, M))，for n in range(N): for mm in rows。
  • wave_unique_bytes：按 wave 切片，len({m}) * a + len({n}) * b。
  • stream_k：g0, g1 = s*T//n, (s+1)*T//n；while 循环：tile, k = divmod(g, k_iters)，end = min(g1, (tile+1)*k_iters)。
  • fixup_tiles：defaultdict(set) 记录每个 tile 出现在哪些 SM。
L3详解：答案几乎是答案（重度剧透）
关键问题答案
  1. 32×32 = 1024 个 tile，170 个 SM：7 波，最后一波 4 个，利用率 86%（wave_stats(1024, 170)）。8192³ 是 96%。
  2. 同一波里的 tile 共享的 A 行块和 B 列块越多，同时需要的数据越少，L2 越容易装下、命中越高。一波 132 个 tile 排成一整行要 132 个不同的 B 块；排成 8×16 的方块只要 8 + 16 个。
  3. 部分和要写到 global workspace、再读回来（一个 128×128 FP32 tile 是 64 KB），还要一个 flag 做同步；切开的 tile 越多开销越大。tile 数正好是 SM 数的整数倍、或者 K 很小时不值得。
  4. 每个 tile 的 prologue（TMEM 分配、barrier 初始化、描述符预取）只做一次；更重要的是 epilogue 可以和下一个 tile 的 mainloop 重叠（B4、C1 的双缓冲）。

"""C3 · Tile scheduling: wave quantization, raster swizzle, persistent CTAs and Stream-K — reference solution.

kernel 内部越快，“哪个 SM 算哪个 tile”就越重要。三件事：
1. wave quantization：132 个 SM、200 个 tile，第二波只有 68 个 tile，SM 利用率 76%。
2. L2 局部性：同时在跑的那一波 tile 共用越多 A 行块 / B 列块，L2 命中越高。CUTLASS 的
   raster order + swizzle 把一波 tile 排成“矮胖的方块”而不是“一整行”。
3. persistent kernel：grid = SM 数，每个 CTA 循环取 tile；Stream-K 再把 K 维也切开，
   让每个 SM 分到几乎一样多的 MAC 迭代，尾 tile 由多个 SM 各算一段 K 再做 fixup（部分和归约）。

- wave_stats(num_tiles, num_sms, ctas_per_sm=1) -> dict：slots = num_sms·ctas_per_sm；
  {"waves": ceil(num_tiles/slots), "last_wave": 最后一波的 tile 数, "efficiency": num_tiles / (waves·slots)}；
  num_tiles = 0 时 waves = 0、last_wave = 0、efficiency = 1.0。
- raster_order(m_tiles, n_tiles, swizzle=1) -> list[(m, n)]：把 m 方向按 swizzle 行一组切成条带
  （最后一条可以较短），条带按 m 递增；条带内 n 从 0 到 n_tiles−1，每个 n 再按 m 递增走完条带内的行。
  swizzle = 1 就是行优先。swizzle < 1 抛 ValueError。
- wave_unique_bytes(order, wave, a_tile_bytes, b_tile_bytes) -> int：把 order 按每 wave 个切成若干波，
  每波读 “不同 m 的个数 × a_tile_bytes + 不同 n 的个数 × b_tile_bytes”，返回各波之和
  （假设 L2 只能留住当前这一波的数据）。
- persistent_static(num_tiles, num_sms) -> list[list[int]]：SM s 依次处理 tile s, s+num_sms, …。
- stream_k(num_tiles, k_iters, num_sms) -> list[list[(tile, k_begin, k_end)]]：总迭代数
  T = num_tiles·k_iters 按 SM 平分：SM s 负责全局迭代 [s·T // num_sms, (s+1)·T // num_sms)；
  全局迭代 g 属于 tile g // k_iters 的第 g % k_iters 步。把每个 SM 的区间按 tile 边界切成段。
- fixup_tiles(assign) -> dict[int, int]：被不止一个 SM 分段处理的 tile → 参与的 SM 个数。
- makespan(assign) -> int：所有 SM 中最多的迭代数（每段 k_end − k_begin 之和）。

API
    wave_stats(num_tiles, num_sms, ctas_per_sm=1) -> dict
    raster_order(m_tiles, n_tiles, swizzle=1) -> list[tuple[int, int]]
    wave_unique_bytes(order, wave, a_tile_bytes, b_tile_bytes) -> int
    persistent_static(num_tiles, num_sms) -> list[list[int]]
    stream_k(num_tiles, k_iters, num_sms) -> list[list[tuple[int, int, int]]]
    fixup_tiles(assign) -> dict[int, int]
    makespan(assign) -> int
"""
from __future__ import annotations

import math
from collections import defaultdict


def wave_stats(num_tiles: int, num_sms: int, ctas_per_sm: int = 1) -> dict:
    """几波、最后一波几个 tile、整体利用率。"""
    slots = num_sms * ctas_per_sm
    if num_tiles == 0:
        return {"waves": 0, "last_wave": 0, "efficiency": 1.0}
    waves = math.ceil(num_tiles / slots)
    last = num_tiles - (waves - 1) * slots
    # 132 SM、200 tile：2 波，第二波 68 个，利用率 200 / 264 = 76%。
    # 这个损失和 kernel 写得多好无关，只能靠换 tile 大小、split-K / Stream-K 来补。
    return {"waves": waves, "last_wave": last, "efficiency": num_tiles / (waves * slots)}


def raster_order(m_tiles: int, n_tiles: int, swizzle: int = 1) -> list[tuple[int, int]]:
    """按 swizzle 行一组的条带，条带内按列走。"""
    if swizzle < 1:
        raise ValueError("swizzle must be >= 1")
    # 行优先：一波 132 个 tile 可能是一整行再多一点 —— 用到 1~2 个 A 行块，却要 132 个不同的 B 列块。
    # 条带化后一波是 swizzle × (132 / swizzle) 的小方块，A、B 两边都只读十几块，L2 能装下、能复用。
    out = []
    for m0 in range(0, m_tiles, swizzle):
        rows = range(m0, min(m0 + swizzle, m_tiles))
        for n in range(n_tiles):
            for mm in rows:
                out.append((mm, n))
    return out


def wave_unique_bytes(order, wave: int, a_tile_bytes: int, b_tile_bytes: int) -> int:
    """每波读的不同 A 块 + 不同 B 块的字节数，求和。"""
    total = 0
    for i in range(0, len(order), wave):
        chunk = order[i:i + wave]
        total += len({m for m, _ in chunk}) * a_tile_bytes + len({n for _, n in chunk}) * b_tile_bytes
    return total


def persistent_static(num_tiles: int, num_sms: int) -> list[list[int]]:
    """persistent kernel 的静态轮转。"""
    # grid 只有 num_sms 个 CTA：省掉每个 tile 一次的 CTA 启动 / 初始化（barrier、TMEM 分配、descriptor 预取），
    # epilogue 还能和下一个 tile 的 mainloop 重叠。但 tile 数不能被 SM 数整除时，尾巴照样不齐。
    return [list(range(s, num_tiles, num_sms)) for s in range(num_sms)]


def stream_k(num_tiles: int, k_iters: int, num_sms: int) -> list[list[tuple[int, int, int]]]:
    """按 MAC 迭代平分给各 SM，区间在 tile 边界处切开。"""
    T = num_tiles * k_iters
    out = []
    for s in range(num_sms):
        g0, g1 = s * T // num_sms, (s + 1) * T // num_sms
        segs = []
        g = g0
        while g < g1:
            tile, k = divmod(g, k_iters)
            end = min(g1, (tile + 1) * k_iters)
            segs.append((tile, k, k + (end - g)))
            g = end
        out.append(segs)
    # 每个 SM 的迭代数相差至多 1，所以没有“尾波”。代价：被切开的 tile 要把部分和写到 workspace，
    # 由最后一段（或一个专门的 SM）读回来相加——CUTLASS 把这叫 fixup / reduction。
    # CUTLASS 实际默认用 “hybrid”：前面整波用普通 data-parallel，只把最后不满的一两波交给 Stream-K，
    # 这样只有少数 tile 需要 fixup。
    return out


def fixup_tiles(assign) -> dict[int, int]:
    """被多个 SM 分段计算的 tile → SM 个数。"""
    owners = defaultdict(set)
    for s, segs in enumerate(assign):
        for tile, _, _ in segs:
            owners[tile].add(s)
    return {t: len(o) for t, o in sorted(owners.items()) if len(o) > 1}


def makespan(assign) -> int:
    """最忙的 SM 的迭代数。"""
    return max((sum(e - b for _, b, e in segs) for segs in assign), default=0)

面试官追问 & 对照源码

  • “split-K 和 Stream-K 的区别？” split-K 把每个 tile 的 K 均分成固定的 s 份（每个 tile 都要归约）；Stream-K 只在负载均衡需要的地方切，切的位置由总迭代数决定。
  • “Cluster Launch Control 解决什么问题？” 静态 persistent 调度不知道哪些 SM 被别的 kernel 占着（例如 PDL 下上一个 kernel 的尾巴、或通信 kernel）；CLC 让 CTA 动态“偷”还没启动的 CTA 的坐标，既有 persistent 的好处又能适应 SM 数变化。
  • “MoE 的 grouped GEMM 怎么调度？” 每个 expert 的 M 不同，tile 总数在 kernel 里才知道：调度器遍历 problem_shape 数组，把所有 group 的 tile 拉平成一条序列再分给 SM。
  • “FlashAttention 的调度？” FA3/FA4 也是 persistent + 动态取 tile；causal 时不同 Q 块的工作量差一倍，按“工作量从大到小”的顺序取 tile 来减少尾部不齐。
