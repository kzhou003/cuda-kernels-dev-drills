G4 · 5090：PDL + CUDA Graph，测出 kernel 之间省下的时间

在 5090 上把 C4 的时间线测出来：一条 64 个小 kernel 的链，分别用普通 stream、stream + PDL、CUDA Graph、Graph + PDL 发射。你要写的只有几行——griddepcontrol 放在哪、cudaLaunchKernelEx 怎么配——但它们决定了 kernel 之间省下 3/4 的时间还是一点都省不下。

题面速览

  • 在系统中的位置：device 端就是 CUTLASS 的 launch_dependent_grids / wait_on_dependent_grids；host 端是 kernel_launch.h 里的 cudaLaunchAttributeProgrammaticStreamSerialization。SGLang 的 RMSNorm / RoPE 等 kernel 都带 enable_pdl（pos_enc.cuh），整步 decode 录成 CUDA graph（CudaGraphRunner）。
  • 你要实现：mine/g4_pdl_graph.cu 里两处 TODO：(1) device 端 step_kernel 里 pdl_launch_dependents()、prologue（读 w、spin_cycles）、pdl_wait() 的位置；(2) host 端用 cudaLaunchKernelEx + PDL 属性发射 n_kernels 个 kernel（ping-pong 两个 buffer）。
  • 环境：PDL 需要 sm_90+（H100、B200、RTX 50 系都行）；默认 RTX 5090。graph 测试用 torch.cuda.graph。
  • 难点在这几条规则：
    1. launch_dependents 只是“允许下游上 SM”，不发布结果；下游的 wait 仍然等整个上游 grid 完成。所以可以放在入口。
    2. wait 要放在第一次碰上游数据之前：读 x（上游的输出，RAW）和写 y（上游正在读的输入，WAR）都算。
    3. host 端没有 PDL 属性时，griddepcontrol 指令是无害的空操作；有属性时它们才生效。
    4. 在 stream capture 里发射同样有效：graph 里的边会变成 programmatic edge。

验收要点：PDL 开 / 关 × 1、2、7、64 个 kernel 的结果都等于闭式解，且返回正确的 buffer · 不开 PDL 时下一个 kernel 从不早于上一个结束 · 开 PDL 时 15 次交接里至少 12 次提前开始（用 %globaltimer 时间戳）· graph 里录 10 个 kernel、replay 3 次 = 30 步。

直觉与类比

类比 · 接力赛的交接区（C4 的续）

C4 是在纸上画接力赛，这里是真的跑一场：64 棒，每棒在接棒前有一段“热身”（spin_cycles(4000) ≈ 1.7 µs，代表 barrier 初始化、描述符预取、读权重）。stream：教练（CPU）每喊一棒要几 µs。graph：出场顺序提前排好。PDL：下一棒在交接区里先热身，接棒那一刻（griddepcontrol.wait）才真正等。你会看到：没有 graph 时 PDL 只省 12%；有 graph 时 PDL 再省 70%。

逐步演示

▶ 64 个 kernel，每个 prologue 4000 周期（RTX 5090 实测）
1. stream

每个 kernel 4.16 µs：CPU 发射 + GPU 启动延迟 + prologue 1.7 µs + 很短的 main，全部串行。

2. stream + PDL

3.66 µs / kernel，只省 12%：CPU 发射仍然一个一个来，下一个 kernel 常常在上一个结束后才被 CPU 发出来，交接区用不上。

3. CUDA graph

2.25 µs / kernel：CPU 开销没了，剩下 GPU 端的启动间隔 + prologue。

4. graph + PDL

0.68 µs / kernel——比 prologue 本身（1.7 µs）还短：因为每个 kernel 一进来就触发，下游的下游也能接着提前上 SM，多个 kernel 的 prologue 叠在一起跑，只有 main 是串行的。这就是“PDL 只有在 graph 里才真正有用”的实测版本。

（数字来自 ./check.sh g4 --bench --solutions，你的机器上会有出入；spin 越大，PDL 的收益越明显。）

易错点

  • 把读 x 放进 prologue。 能跑、多数时候结果也对，偶尔错——典型的竞态。测试不一定每次都抓得到，所以要靠 C4 的 pdl_hazards 这种推理。
  • 在 wait 之前写 y。 y 是上一个 kernel 正在读的 x（ping-pong），WAR 竞态。
  • 忘了 host 端的属性。 指令照样执行但没有效果：test_with_pdl_next_kernel_starts_before_previous_ends 会发现没有重叠。
  • <<<>>> 发射。 三重尖括号语法没法带属性，必须用 cudaLaunchKernelEx。
  • stamps 指针没按 kernel 偏移。 第 k 个 kernel 写 stamps + 2k。
  • 以为触发越早越好。 这里为了放大效果在入口触发；真实 GEMM 在 epilogue 附近触发，避免下游 CTA 和上游 mainloop 抢 SMEM / 寄存器。

关键问题

  1. launch_dependents 放在入口安全吗？为什么？
  2. prologue 里能读 w 吗？能读 x 吗？能写 y 吗？
  3. 为什么测试用 %globaltimer 而不是 clock64()？
  4. 不开 PDL 时，为什么下一个 kernel 的开始时间一定晚于上一个 kernel block 0 的结束时间？

L3详解：答案几乎是答案（重度剧透）
关键问题答案
  1. 安全：触发只影响“下游什么时候能被调度”，下游的 griddepcontrol.wait 依然要等本 grid 全部完成且内存可见。代价只是下游 CTA 更早占用 SM 资源。
  2. w 能读（没有任何 kernel 写它）；x 不能（上游的输出，RAW）；y 不能写（上游的输入，WAR）。
  3. clock64() 是每个 SM 自己的周期计数器，不同 SM、不同 kernel 之间不可比；%globaltimer 是全局纳秒计时器。
  4. 没有 PDL 时，同一个 stream 上下一个 kernel 要等上一个 kernel 的所有 block 都结束才启动，block 0 的结束时间早于（或等于）整个 grid 的结束。

// G4 · Programmatic Dependent Launch (PDL) + CUDA Graph on a chain of small kernels (sm_90+; RTX 5090 = sm_120)
//
// A decode step is a chain of hundreds of tiny kernels. This drill builds such a chain:
//   x_{i+1} = a · x_i + w        (n_kernels launches, ping-ponging between two buffers)
// and gives every kernel a "prologue" that does not depend on the previous kernel's output — it reads its own
// weights and then spins for `spin` cycles to stand in for the real setup work (SMEM carve-up, mbarrier init,
// TMA descriptor prefetch, loading weights / scales).
//
// With PDL:
//   * device side: the kernel calls griddepcontrol.launch_dependents early (here: at entry), so the NEXT kernel's
//     CTAs may be scheduled while this one is still running; and it calls griddepcontrol.wait right before the
//     first access that touches the previous kernel's data. wait blocks until the previous grid has completed and
//     its memory is visible. Everything before wait overlaps with the previous kernel.
//   * host side: launch with cudaLaunchKernelEx + cudaLaunchAttributeProgrammaticStreamSerialization = 1.
//     Without that attribute the griddepcontrol instructions are harmless no-ops and launches serialize as usual.
//   * Both work inside stream capture: the graph keeps "programmatic" edges between the kernel nodes.
//
// Each kernel's block 0 also records %globaltimer (ns) at entry and at exit into `stamps` (if not null), so the
// tests can observe the overlap: with PDL, kernel i+1 starts before kernel i has finished.
#include <torch/extension.h>
#include <c10/cuda/CUDAStream.h>
#include <c10/cuda/CUDAException.h>
#include <cuda_runtime.h>
#include <cstdint>

// ---------------------------------------------------------------- given device helpers
__device__ __forceinline__ uint64_t global_ns() {
  uint64_t t;
  asm volatile("mov.u64 %0, %globaltimer;" : "=l"(t));
  return t;
}
__device__ __forceinline__ void spin_cycles(long long n) {
  long long start = clock64();
  while (clock64() - start < n) {
  }
}
__device__ __forceinline__ void pdl_launch_dependents() {
  asm volatile("griddepcontrol.launch_dependents;" ::: "memory");
}
__device__ __forceinline__ void pdl_wait() {
  asm volatile("griddepcontrol.wait;" ::: "memory");
}

// ---------------------------------------------------------------- the kernel
// y = a * x + w.  x is the previous kernel's output; y is the buffer the previous kernel READ (ping-pong),
// so writing y early is a write-after-read hazard, and reading x early is a read-after-write hazard.
__global__ void step_kernel(const float* __restrict__ x, float* __restrict__ y, const float* __restrict__ w, int n,
                            float a, long long spin, bool use_pdl, unsigned long long* stamps) {
  const int i = blockIdx.x * blockDim.x + threadIdx.x;
  if (stamps && blockIdx.x == 0 && threadIdx.x == 0) stamps[0] = global_ns();

  // >>> SOLUTION (where do launch_dependents and wait go?)
  // Let the next kernel get onto the SMs as early as possible. Triggering does NOT publish our results — the
  // dependent's griddepcontrol.wait still waits for this whole grid to finish — so triggering at entry is safe.
  if (use_pdl) pdl_launch_dependents();

  // prologue: touches nothing the previous kernel writes or reads
  const float wi = i < n ? w[i] : 0.f;
  spin_cycles(spin);

  // first access to the previous kernel's output (x) and to its input (y): wait here, not earlier
  if (use_pdl) pdl_wait();
  // <<< SOLUTION

  if (i < n) y[i] = a * x[i] + wi;
  if (stamps && blockIdx.x == 0 && threadIdx.x == 0) stamps[1] = global_ns();
}

// Launch `n_kernels` steps on the current stream: buf0 -> buf1 -> buf0 -> ...; returns the buffer holding the result.
torch::Tensor run_chain(torch::Tensor buf0, torch::Tensor buf1, torch::Tensor w, int64_t n_kernels, double a,
                        int64_t spin, bool use_pdl, c10::optional<torch::Tensor> stamps) {
  TORCH_CHECK(buf0.is_cuda() && buf0.dtype() == torch::kFloat32 && buf0.is_contiguous());
  TORCH_CHECK(buf1.sizes() == buf0.sizes() && w.sizes() == buf0.sizes() && buf1.is_contiguous() && w.is_contiguous());
  const int n = buf0.numel();
  unsigned long long* st = nullptr;
  if (stamps.has_value()) {
    TORCH_CHECK(stamps->dtype() == torch::kInt64 && stamps->numel() >= 2 * n_kernels && stamps->is_contiguous());
    st = reinterpret_cast<unsigned long long*>(stamps->data_ptr<int64_t>());
  }
  cudaStream_t stream = c10::cuda::getCurrentCUDAStream();
  float* bufs[2] = {buf0.data_ptr<float>(), buf1.data_ptr<float>()};
  const float* wp = w.data_ptr<float>();

  // >>> SOLUTION (host: cudaLaunchKernelEx with the programmatic-stream-serialization attribute)
  cudaLaunchConfig_t cfg = {};
  cfg.gridDim = dim3((n + 255) / 256);
  cfg.blockDim = dim3(256);
  cfg.dynamicSmemBytes = 0;
  cfg.stream = stream;
  cudaLaunchAttribute attr[1];
  attr[0].id = cudaLaunchAttributeProgrammaticStreamSerialization;
  attr[0].val.programmaticStreamSerializationAllowed = use_pdl ? 1 : 0;
  cfg.attrs = attr;
  cfg.numAttrs = 1;
  for (int64_t k = 0; k < n_kernels; ++k) {
    const float* x = bufs[k % 2];
    float* y = bufs[(k + 1) % 2];
    C10_CUDA_CHECK(cudaLaunchKernelEx(&cfg, step_kernel, x, y, wp, n, static_cast<float>(a),
                                      static_cast<long long>(spin), use_pdl, st ? st + 2 * k : nullptr));
  }
  // <<< SOLUTION
  return n_kernels % 2 ? buf1 : buf0;
}

面试官追问 & 对照源码

  • “为什么说 PDL 是 graph / compiler 层面的优化？” 见 C4：要上下游三方配合、CPU 发射开销要先被 graph 去掉。本题的四个数字就是证据。
  • “torch.compile 会自动加 PDL 吗？” mode="reduce-overhead" 自动用 CUDA graph；PDL 需要每个 kernel 自己有 griddepcontrol 并以属性启动，Triton 生成的 kernel 和 Inductor 正在逐步支持。推理框架（SGLang、FlashInfer、TensorRT-LLM）是手动在关键 kernel 上加的。
  • “PDL 和多 stream 并发有什么区别？” 多 stream 是没有依赖的 kernel 并发；PDL 是有依赖的 kernel 部分重叠（依赖之前的部分）。
  • “上游 kernel 有 persistent 调度时呢？” persistent kernel 的 CTA 一直占着 SM，下游提前启动也没地方放；所以 CUTLASS 在 persistent kernel 的最后一个 tile 才触发。
